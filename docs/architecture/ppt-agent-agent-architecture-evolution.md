# PPT Agent 智能体架构演进记录

本文档记录 PPT Agent 在生成架构上的几次主要迁移，以及每次迁移背后的问题、收益和下一步方向。整体演进主线是：**逐步放大 LLM 擅长的理解、规划、归纳和策略能力，同时限制 LLM 在确定性执行环节的自由度**。

这里的 `ReAct` 指 Agent 范式中的 Reasoning + Acting，不是前端 React 框架。

## 1. 总体演进脉络

```text
ReAct 自由工具调用
  ↓
Plan-Execute-Replan 串行规划执行
  ↓
DeepAgent + tasks.json + SlideExecutor 子 Agent
  ↓
Planner-Compiler-Renderer 工作流
```

这条路径不是简单追逐某个 Agent 框架，而是在逐步回答一个问题：**PPT 生成中哪些部分应该交给 LLM，哪些部分应该交给代码和工具链？**

结论逐渐清晰后，系统边界应收敛为：

```text
LLM 负责不确定性：
- 理解用户需求
- 选择表达角度
- 拆解页面结构
- 组织内容计划
- 搜索和归纳事实、案例、背景素材方向
- 在失败或质量问题发生时提出修复策略

代码负责确定性：
- schema 校验
- 页面容量校验
- 背景和素材引用校验
- 并发调度
- 调用 Python generator
- 状态写回
- PPT 合并、缩略图、下载交付
```

## 2. 阶段一：ReAct 自由工具调用

早期思路更接近 ReAct：Agent 在一次长循环中不断思考、选择工具、读取文件、编写代码或脚本，并尝试完成整套 PPT。

这种方式的优势是灵活，适合探索性任务。例如需求不明确、需要边查边想、工具边界尚未定型时，ReAct 可以快速把链路跑起来。

但 PPT 属于长规划、强结构、强视觉一致性的任务，ReAct 很快暴露出劣势：

- 长任务中上下文持续膨胀，模型容易遗忘前面页面的约束。
- 每一步都由模型临场决定，轨迹难以稳定复现。
- 页面之间缺少全局节奏控制，容易出现重复、遗漏和风格漂移。
- 工具调用次数多，成本高，失败点分散。
- 生成结果更像“模型即时发挥”，而不是一套可编译、可检查的交付计划。

这一阶段的核心教训是：**PPT 不是一组孤立动作，而是一份长程结构化作品。先有整体计划，再执行页面，质量才可控。**

## 3. 阶段二：Plan-Execute-Replan

第二阶段引入 Plan-Execute-Replan，把流程拆成规划、执行、重规划。相比 ReAct，它让 Agent 先形成计划，再按计划执行，解决了一部分“边想边做导致失控”的问题。

当时 PPT 生成仍主要交给 Agent：Agent 需要理解页面需求、编写 Python、调用运行、观察错误，再继续修正。此时还没有稳定依赖 `skills/visual_designer/generators` 中的专用生成器。

这个阶段的收益：

- 有了显式计划，任务结构比 ReAct 更清楚。
- Replan 能在失败后调整路线，而不是完全卡死。
- 更容易把用户需求拆成页面级任务。

但问题也很明显：

- 串行执行耗时长，一页失败会拖住整套 PPT。
- 直接让 Agent 编写 Python，首轮成功率不稳定。
- 每次生成都可能写出不同的绘制逻辑，视觉风格难统一。
- 修复循环成本高，经常在语法、路径、依赖和布局细节上消耗轮次。
- 代码生成自由度太高，导致质量问题难以系统性治理。

这一阶段的核心教训是：**LLM 可以设计页面，但不应该每次从零编写底层 PPT 绘制代码。**

## 4. 阶段三：DeepAgent + Visual Designer 生成器

第三阶段转向 DeepAgent 架构：主 Agent 负责任务规划和 `tasks.json`，子 Agent 作为 `SlideExecutor` 按页执行。与此同时，PPT 绘制能力下沉到 `skills/visual_designer/generators`，通过 `python-pptx` 生成器和模板契约约束页面结构。

典型链路是：

```text
用户需求
  ↓
主 Agent 生成 tasks.json
  ↓
SlideExecutor 子 Agent 读取单页任务
  ↓
调用 Python generator 生成单页 PPTX
  ↓
后端校验输出、生成缩略图、合并交付
```

这个阶段相较上一版有重要进步：

- Python 绘制逻辑从“Agent 临场手写”变成“复用稳定生成器”。
- `content_type`、`content_plan`、`background`、`theme` 等字段逐渐成为跨层契约。
- 单页生成可以限制并发，整体速度优于纯串行。
- 视觉质量问题可以沉淀到生成器和模板，而不是反复调 prompt。
- RuntimeMeta、Timeline、任务状态和输出文件校验让运行过程更可观测。

但这一版最初没有背景图片体系，页面更依赖纯模板和配色，导致不同主题之间的真实感、行业贴合度和视觉丰富度不足。后续补入了背景库、背景 manifest、主题目录、数字命名规则和统一主题约束，解决了一部分“PPT 像模板拼装”的问题。

这一阶段仍然遗留一个结构性矛盾：**单页生成本质已经是确定性工具调用，但系统仍把它包装成子 Agent 执行。**

这会带来新的成本：

- 每个子 Agent 都需要额外 prompt 和上下文。
- 子 Agent 要再次理解 `tasks.json` 中已经规划好的内容。
- 工具调用参数更复杂，容易出现 JSON 畸形或流式截断问题。
- 并发能力受 Agent 调度影响，而不是由后端 worker pool 稳定控制。
- 生成阶段消耗了本应留给规划和素材准备的 token 与时间。

这一阶段的核心教训是：**当页面计划已经结构化后，Agent 不应继续充当 worker。**

## 5. 阶段四：Planner-Compiler-Renderer 工作流

下一版更适合采用工作流优先的架构，而不是继续加深 DeepAgent 子 Agent 层级。目标是把系统拆成准备、编译、渲染、交付四段：

```text
用户需求
  ↓
Planner：生成 DeckSpec / tasks.json
  ↓
Asset Planner：搜索事实、案例和背景图片候选
  ↓
Validator：校验 schema、容量、背景、素材和页面一致性
  ↓
Compiler：把语义 content_plan 转成 generator-ready 参数
  ↓
Renderer Worker Pool：并发 generate_slide(task_id)
  ↓
Merger / Thumbnail / Delivery
  ↓
QA / Fixer：只处理失败页或高风险页
```

这一版的核心变化是：**把重心放到生成前的准备阶段，而不是生成阶段的 Agent 自由发挥。**

准备阶段应该沉淀更多信息：

- 整套 PPT 的主题、受众、表达目标和语气。
- 页面数量、页面节奏、章节结构和每页职责。
- 每页 `content_type`、`layout_variant`、容量上限和必要字段。
- 事实、数据、案例、来源和引用口径。
- 背景图片搜索关键词、候选图片、本地缓存和授权/来源记录。
- 整套 PPT 的统一背景主题、配色和视觉风格。

渲染阶段则应尽量简单：

```json
{
  "tool": "generate_slide",
  "task_id": "3"
}
```

工具根据 `task_id` 读取对应 SlideSpec，完成校验、生成、状态写回和错误记录。并发由后端统一控制，而不是由多个子 Agent 竞争上下文。

## 6. 背景图片搜索应放在准备阶段

背景图片和相关案例天然属于“准备阶段素材规划”，不适合放到每页生成时临时搜索。

合理链路是：

```text
主题理解
  ↓
生成搜索关键词
  ↓
搜索图片和案例素材
  ↓
下载候选资源
  ↓
去重、过滤黑白图、过滤低清图、过滤跑题图
  ↓
统一尺寸、色调和风格
  ↓
写入 deck_assets.json / manifest
  ↓
tasks.json 引用具体背景或主题目录
```

这样可以避免：

- 每页各自搜索导致风格漂移。
- 生成阶段联网导致耗时不稳定。
- 图片来源、授权和可追溯性缺失。
- 背景与页面分类或主题不匹配。

默认策略可以是：

```text
通用场景：
  优先使用本地 10 类背景库

具体行业、城市、产品、案例类场景：
  在准备阶段启动专题背景搜索
  形成本次任务专属素材包
```

长期看，PPT Agent 应从“固定模板生成器”演进为“先构建专题素材包，再编译生成整套 PPT”的系统。

## 7. 迁移原则

后续迁移应遵循以下原则：

1. LLM 不再直接负责确定性绘制。
2. LLM 输出必须尽量结构化，并能被 schema 校验。
3. 每页生成必须可由 `task_id` 独立复现。
4. 并发调度由代码控制，不依赖 Agent 自我调度。
5. 背景、图片、案例和事实来源在准备阶段统一规划。
6. QA 和 Fixer 从默认主链路中退出，只处理异常、高风险或显式启用场景。
7. 所有跨层字段都必须有稳定语义，尤其是 `content_type`、`content_plan`、`background`、`theme`、`output_file`。

## 8. 目标形态

最终目标不是“少用 Agent”，而是让 Agent 站在更合适的位置：

```text
Agent = 规划者、研究员、策展人、诊断者
Workflow = 调度器、状态机、质量门禁
Tool = 可复现的确定性执行器
Generator = PPT 页面编译后端
```

这条路线能同时提升速度、稳定性、视觉一致性和可维护性，也能减少上下文消耗、工具调用畸形和长任务中模型漂移的问题。
