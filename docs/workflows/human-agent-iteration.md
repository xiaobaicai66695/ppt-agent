# PPT Agent 人机协作迭代工作流

> 本工作流定义用户与 Agent 在 PPT Agent 工作区中的协作节奏、交付物标准和需求转轨规则。

**版本**: 2.2
**日期**: 2026-08-05
**状态**: 已实施

---

## 1. 核心理念

- **按规模分流**: 小需求允许当场闭环；中大型需求必须先映射到 `docs/issues/todo.md` 中的长期方向。
- **按需预研**: 只有在边界不清、依赖外部系统或存在方案权衡时，才编写 `docs/research/` 预研文档。
- **双路线推进**: 已登记事项可以直接开始做（`direct`），也可以进入 OPSX/OpenSpec 工作流（`opsx`）。
- **上线后再闭环**: 影响运行行为的变更必须完成部署、重启确认和线上低成本冒烟，不能以本地测试通过代替交付完成。
- **透明可追踪**: 长期方向在 `todo.md` 汇总，实施状态由 research/OpenSpec/迭代记录承载，完成事项在 `done.md` 归档。

---

## 2. 事项登记入口

### 2.1 文件位置

```
docs/issues/todo.md
docs/issues/done.md
```

- `todo.md`：只保留长期迭代方向。
- `done.md`：归档已经完成的错误修复、UI 改造和其他具体执行事项。

### 2.2 由谁更新

- **Agent**: 对于中大型需求，或虽然是小需求但明显无法当场闭环时，第一个动作是确认所属长期方向；若现有方向无法覆盖，则追加新方向。
- **User**: 可随时直接编辑此文件，修正或补充需求描述。

### 2.3 时间、方向与归档顺序

- `todo.md` 的新方向按首次提出时间追加，不得插入或重排既有方向。
- 具体事项的 `计划时间` 和 `完成时间` 统一使用 `YYYY-MM-DD`，在完成时连同产出链接追加到 `done.md`。
- `done.md` 保留历史 ID 和原始顺序；归档后不因分类变化重排历史条目。

## 3. 需求分类与判定标准

| 类型 | 特征 | 默认动作 | 举例 |
|------|------|----------|------|
| **small** | 单点修改、已有模式复用、通常可在当前会话闭环 | 可直接开始；若中途失控则补登记 | 文档 typo、配置调整、小修复、测试补充 |
| **medium** | 涉及多个文件或模块，需要跨会话跟踪 | 必须先登记到 `todo.md` | 一组相关 CLI 改动、配置机制扩展、较大文档更新 |
| **large** | 跨层级、涉及设计决策、影响公共接口或协议 | 必须先登记到 `todo.md`，通常优先考虑 `opsx` | 新系统接入、新增 MCP 工具族、接口变更、架构调整 |

## 4. 流转规则

### 4.1 小需求 —— 当场闭环或升级登记

```
用户提出需求
    │
    ▼
Agent 判断是否可在当前会话内闭环
    │
    ▼
← 可闭环：直接实现并完成本地验证
             │
             ▼
          运行行为变更：部署、重启确认、线上冒烟和清理
             │
             ▼
          回填证据并归档到 done.md
← 不可闭环/复杂度超出预期：登记到 todo.md，再按 medium/large 规则继续
```

### 4.2 中大型需求 —— 先登记再分流

```
用户提出需求
    │
    ▼
Agent 确认 todo.md 中的长期方向
    │
    ▼
按需补充 research（状态: researching）
    │
    ▼
选择路线：direct 或 opsx
    │
    ▼
← direct：进入实现（状态: in_progress）
← opsx：进入 openspec/changes/<change>/（状态: in_opsx）
    │
    ▼
实现并完成本地验证
    │
    ▼
运行行为变更：部署、重启确认、线上冒烟和清理
    │
    ▼
回填上线证据，归档到 done.md，并更新方向基线
```

### 4.3 何时写 `docs/research/`

满足任一条件时，建议先补预研：

- 需求边界不清，用户口径尚未稳定
- 依赖外部系统、外部 API 或新三方库
- 有两个及以上可行方案需要比较
- 预计会影响项目架构、接口契约或长期维护成本

不满足以上条件时，不强制产出预研文档。

## 5. 后续工作流产出物规范

实施中的产出物由对应 research、OpenSpec change 或迭代记录持续维护；完成后汇总到 `done.md`。推荐位置如下：

| 阶段 | 标准产出物 | 路径示例 |
|------|-----------|---------|
| Research | 预研文档（可选） | `docs/research/YYYY-MM-DD-short-title.md` |
| Direct | 直接实现相关链接 | 代码路径、PR、补充文档 |
| OPSX | 正式变更目录 | `openspec/changes/<change>/` |
| Deploy | Linux 交付与重启记录 | 部署目标、时间、进程标识、启动日志摘要 |
| Smoke | 线上最小代表性验证 | 接口状态、测试任务 ID/结果、清理结果、遗留风险 |
| Final | 最终产出 | 代码路径、测试文件、补充文档 |

> 对于 `opsx` 路线，不在本工作流中硬编码 proposal/spec/design/tasks 的固定顺序，统一以当前 OPSX schema 和 `openspec status --change <name>` 输出为准。

## 6. 上线与冒烟门禁

### 6.1 适用范围

- 后端、前端、Agent、prompt、生成器、模板、运行配置等会改变服务器行为的变更，必须走上线冒烟。
- 纯文档、仅测试或明确不会进入运行环境的变更可以免部署，但必须在最终说明和归档记录中写明原因。
- 因权限、凭据、外部服务或基础设施问题无法上线时，记录阻塞证据并保留未闭环状态，不得以“本地已通过”替代线上结果。

### 6.2 标准步骤

1. 完成与风险匹配的本地测试和构建。
2. 构建 Linux 交付物并部署到已确认的服务器目录。
3. 按线上现有启动方式重启服务，确认新进程、监听端口和启动日志。
4. 执行最小代表性冒烟测试。
5. 清理冒烟产生的任务、文件和部署临时产物。
6. 将部署目标、时间、进程标识、接口状态、任务结果和遗留风险回填到迭代记录、OpenSpec tasks 或 `done.md`。
7. 冒烟通过后才允许归档 `done.md`；`opsx` 路线随后才能完成验证并 archive。

### 6.3 最小冒烟矩阵

| 改动类型 | 最低检查项 |
|----------|------------|
| 通用服务 | `/api/health` 返回 200，新进程稳定，启动日志无立即失败 |
| 前端 | 首页可访问，受影响的关键工作台页面和操作可用 |
| 模板/素材 | `/api/templates` 或对应资源接口正常，真实缩略图/资源可加载 |
| 鉴权 | 登录成功，受保护接口携带有效会话可访问，失效会话行为符合预期 |
| PPT 生成链路 | 创建 1 个 1-2 页低成本任务，核对元数据总页数/已生成页数、最终状态、PPTX 和缩略图 |
| 可观测性/SSE | 关键阶段事件可见，连接结束状态正确，无明显重复或提前完成事件 |

> 冒烟测试应控制成本和影响面，不默认运行全量模板、长篇 PPT、QA 或大量模型请求。

## 7. Agent 行为准则

1. **先判断规模再行动**: Agent 必须先判断事项是 `small`、`medium` 还是 `large`。
2. **中大型事项先归类**: 对 `medium` / `large` 事项，Agent 在动手前必须确认所属长期方向；无法归类时先向 `todo.md` 追加新方向。
3. **小需求失控就升级**: 原本按 `small` 处理的事项，只要出现跨会话、跨层级、边界不清等迹象，必须补登记。
4. **预研按需而不是滥写**: 只有在不确定性真实存在时才创建 `docs/research/` 文档。
5. **路线必须显式**: 具体事项必须标明 `direct` 或 `opsx`，并在 research、OpenSpec 或迭代记录中持续回填链接。
6. **本地验证要聚焦**: 按改动范围选择最小有效验证。Go 后端使用相关包的 `go test` 和必要的 `go build ./...`；Vue 前端使用 `npm run build`；Python PPT 生成器至少执行相关文件的 `py_compile`，视觉改动按需生成 PPTX 并渲染检查；OpenSpec 事项执行 `openspec validate <change> --strict`。
7. **上线冒烟是完成门禁**: 影响运行行为的变更必须在本地验证后完成部署、重启确认、线上冒烟、测试数据清理和证据回填，才可以标记完成。
8. **每日汇报**: 在日常汇报中，按长期方向列出活跃的 research、OpenSpec change 和 blocked 事项，不重复罗列 `done.md` 历史记录。

## 8. 示例场景

### 场景 A：简单需求（文档更新）

> 用户：“README 里架构图的一处文字写错了。”

- Agent 判断该事项可在当前会话内闭环，因此不强制登记到 `todo.md`。
- 当场修改 README 并验证。
- 若过程中发现影响多个文档或需要跨会话跟踪，再补登记。

### 场景 B：复杂需求（外部模板服务接入）

> 用户：“为 PPT Agent 接入企业模板素材服务。”

- Agent 先将需求映射到 `todo.md` 的相关长期方向；若是全新方向才追加方向记录。
- 用户确认边界（只读取模板索引，还是还要同步图片、字体和授权信息）。
- 如需对接外部 API、鉴权或新增缓存机制，先补 `docs/research/` 预研文档。
- Agent 创建 `openspec/changes/<change>/` 并按当前 schema 推进。
- 实现和本地验证完成后部署到目标服务器，执行对应接口与最小任务冒烟并清理测试数据。
- 上线冒烟通过后将 ID、时间、产出链接和上线证据归档到 `done.md`，并更新长期方向基线。

### 场景 C：中等需求（直接实现）

> 用户：“给现有缩略图接口补批量预热能力，沿用当前 TaskManager 和转换器实现。”

- Agent 判断该事项涉及多个文件，属于 `medium`。
- 先确认 `todo.md` 中的所属方向，并在迭代记录中标明 `route=direct`。
- 若无需方案权衡，则不写 `docs/research/`。
- 直接进入实现；完成本地测试、部署和线上批量预热接口冒烟后，将产出物路径、上线证据和状态归档到 `done.md`。
