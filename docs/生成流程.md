# PPT 生成流程

## 一、前端发起请求

用户在前端输入需求后，前端调用 `POST /api/tasks`，传入 `query`。如果用户已经在编排页整理了完整大纲，还会传入 `outline`，包括每页标题、页面类型、配色、图片策略等结构化信息。后端 `handleCreateTask` 接收请求并生成唯一 `taskID`。

## 二、任务初始化

任务初始化由 `task/manager.go` 负责：

1. 创建工作目录 `workDir = {baseDir}/{userID}-{taskID}/`。
2. 初始化 `TaskState`，记录用户请求、运行元数据和 SSE 状态。
3. 如果请求包含 `outline`，先把它写成 `tasks.draft.json` 的结构化种子，但仍交给 Planner 完成整套规划。
4. 如果请求只有自然语言需求，则由 Planner 从空草稿生成完整 `tasks.draft.json`。
5. 启动后台 goroutine 执行生成链路。

## 三、意图分类与推荐

后端先调用意图分类器，输出稳定的路由与推荐结果：

- `agent_type=planner`
- `pipeline=["plan","generate"]`
- 推荐组件化 preset、配色、页数和图片策略
- 是否需要搜索并嵌入背景图或实景图
- 渲染并发数

该阶段的目标是把用户需求压缩成明确的生成约束，减少 Planner 在后续阶段反复猜测。

## 四、Planner 生成 DeckSpec

Planner 使用 `pkg/prompts/planner/master_instruction.tmpl`，只负责不确定性高的规划工作：

- 理解用户主题和场景。
- 拆分页面结构。
- 为每页选择合法 `content_type` 和 `layout_variant`。
- 组织 `description` 与 `content_plan`。
- 为背景图或实景图生成合适搜索词，并引用任务工作区中的下载图片。
- 通过 `update_tasks_manifest(mode=initialize)` 一次性写入 `tasks.draft.json`。

Planner 不负责审查、提交、编写 Python 或直接绘制 PPT 页面。它只产出完整的 DeckSpec 草稿。

## 五、Task Reviewer 与 DeckSpec 锁定

Go workflow 对 `tasks.draft.json` 执行确定性校验。发现阻断问题时，独立的 `TaskPlanReviewer` 读取审查报告并通过 `patch_tasks_draft` 定点修订；最多执行三轮。

质量门通过后，Go 校验审查指纹并原子提交正式 `tasks.json`。Planner 和 Reviewer 都不能绕过该步骤直接发布正式清单；草稿缺失、模型参数格式异常和重试上限也由代码处理。

## 六、DeckSpec 渲染校验

进入渲染前，`deck_renderer.go` 会读取并校验 `tasks.json`：

- 工作目录和 skills 目录必须存在。
- `tasks.json` 必须存在且包含至少一页。
- 每页必须有稳定的 `task_id`、`page_index`、`content_type` 和输出文件名。
- 已完成且文件存在的页面会跳过，缺失或 pending/failed 页面进入渲染队列。

校验通过后，RuntimeMeta 会冻结页面计划，前端可以展示真实的总页数和进度。

## 七、并发渲染

渲染阶段由 Eino workflow 中的 worker pool 执行：

```text
validate_deck_spec
    ↓
render_worker_pool
    ↓
generate_slide(task_id)
    ↓
ReconcileTasksManifestOutputFiles
```

每个 worker 只接收一个 `task_id`，Python `render_task.py` 根据 `task_id` 读取 `tasks.json` 中对应页面，再调用 `skills/ppt-deck-planner/generators` 下的确定性生成器。生成成功后，后端把页面状态更新为 `done`；失败则写入 `failed` 和错误摘要。

## 八、合并、预览与交付

所有页面渲染结束后，任务管理器会：

1. 对账 `tasks.json` 与实际 PPTX 文件。
2. 合并单页 PPTX。
3. 生成缩略图。
4. 更新任务状态、文件列表和交付元数据。
5. 通过 SSE 推送 `progress`、`file_ready`、`complete` 或 `error`。

前端任务页根据 SSE 和轮询接口展示进度、缩略图、运行事件和下载入口。

## 九、后续对话改进

任务完成后，用户可以继续发起修改请求。后端先做意图分类，再根据意图走统一的 DeckSpec patch 与重渲染路径：

- `fix`：由 `PPTFixer` 只修改后端授权的目标页，不能新增、删除、重排页面或修改运行身份字段。
- `regenerate`：把指定页面标记为待生成并重新渲染。
- `regenerate_all`：整套页面重新渲染。
- `add_page`：追加新页面任务并渲染。
- `needs_clarification`：请求用户补充页面范围或修改目标。

续聊不再回到 Planner。定点修复由 `PPTFixer` 更新获准页面后复用同一套 worker pool，恢复与失败兜底仍由 Go 负责。

## 十、流程图

```text
用户需求
    ↓
前端 POST /api/tasks
    ↓
TaskManager 创建任务
    ↓
意图分类与模板/图片策略推荐
    ↓
PPTPlanner 生成完整 tasks.draft.json
    ↓
Go 校验 → TaskPlanReviewer 修订（最多三轮）
    ↓
指纹校验并原子提交 tasks.json
    ↓
Worker Pool 并发 generate_slide(task_id)
    ↓
对账、合并、缩略图
    ↓
SSE 推送进度与完成状态
    ↓
前端展示预览和下载入口
```
