# PPT 生成流程

## 一、前端发起请求

用户在前端输入需求后，前端调用 `POST /api/tasks`，传入 `query`。如果用户已经在编排页整理了完整大纲，还会传入 `outline`，包括每页标题、页面类型、配色、背景等结构化信息。后端 `handleCreateTask` 接收请求并生成唯一 `taskID`。

## 二、任务初始化

任务初始化由 `task/manager.go` 负责：

1. 创建工作目录 `workDir = {baseDir}/{userID}-{taskID}/`。
2. 初始化 `TaskState`，记录用户请求、运行元数据和 SSE 状态。
3. 如果请求包含完整 `outline`，先把 outline 转成 `tasks.json`，后续 Planner 只补齐缺失内容。
4. 如果请求只有自然语言需求，则等待 Planner 生成完整 `tasks.json`。
5. 启动后台 goroutine 执行生成链路。

## 三、意图分类与推荐

后端先调用意图分类器，输出稳定的路由与推荐结果：

- `agent_type=planner`
- `pipeline=["plan","generate"]`
- 推荐模板、配色、页数和背景主题
- 是否启用背景图片
- 渲染并发数

该阶段的目标是把用户需求压缩成明确的生成约束，减少 Planner 在后续阶段反复猜测。

## 四、Planner 生成 DeckSpec

Planner 使用 `pkg/prompts/planner/master_instruction.tmpl`，只负责不确定性高的规划工作：

- 理解用户主题和场景。
- 拆分页面结构。
- 为每页选择合法 `content_type` 和 `layout_variant`。
- 组织 `description` 与 `content_plan`。
- 选择同一背景主题目录下的背景引用。
- 通过 `update_tasks_manifest` 写入 `tasks.json`。

Planner 不负责编写 Python，也不直接绘制 PPT 页面。它的输出必须是可校验、可并发渲染的 DeckSpec。

## 五、DeckSpec 校验

进入渲染前，`deck_renderer.go` 会读取并校验 `tasks.json`：

- 工作目录和 skills 目录必须存在。
- `tasks.json` 必须存在且包含至少一页。
- 每页必须有稳定的 `task_id`、`page_index`、`content_type` 和输出文件名。
- 已完成且文件存在的页面会跳过，缺失或 pending/failed 页面进入渲染队列。

校验通过后，RuntimeMeta 会冻结页面计划，前端可以展示真实的总页数和进度。

## 六、并发渲染

渲染阶段由 Eino workflow 中的 worker pool 执行：

```text
validate_deck_spec
    ↓
render_worker_pool
    ↓
generate_slide(task_id)
    ↓
ReconcileTasksManifestOutputFiles
```

每个 worker 只接收一个 `task_id`，Python `render_task.py` 根据 `task_id` 读取 `tasks.json` 中对应页面，再调用 `skills/visual_designer/generators` 下的确定性生成器。生成成功后，后端把页面状态更新为 `done`；失败则写入 `failed` 和错误摘要。

## 七、合并、预览与交付

所有页面渲染结束后，任务管理器会：

1. 对账 `tasks.json` 与实际 PPTX 文件。
2. 合并单页 PPTX。
3. 生成缩略图。
4. 更新任务状态、文件列表和交付元数据。
5. 通过 SSE 推送 `progress`、`file_ready`、`complete` 或 `error`。

前端任务页根据 SSE 和轮询接口展示进度、缩略图、运行事件和下载入口。

## 八、后续对话改进

任务完成后，用户可以继续发起修改请求。后端先做意图分类，再根据意图走统一的 DeckSpec patch 与重渲染路径：

- `fix`：调整指定页面或元素的描述、结构化计划或视觉要求。
- `regenerate`：把指定页面标记为待生成并重新渲染。
- `regenerate_all`：整套页面重新渲染。
- `add_page`：追加新页面任务并渲染。
- `needs_clarification`：请求用户补充页面范围或修改目标。

续聊不再启动独立的页面执行代理，而是更新 `tasks.json` 后复用同一套 worker pool。

## 九、流程图

```text
用户需求
    ↓
前端 POST /api/tasks
    ↓
TaskManager 创建任务
    ↓
意图分类与模板/背景推荐
    ↓
Planner LLM 生成或补齐 tasks.json
    ↓
DeckSpec 校验
    ↓
Worker Pool 并发 generate_slide(task_id)
    ↓
对账、合并、缩略图
    ↓
SSE 推送进度与完成状态
    ↓
前端展示预览和下载入口
```
