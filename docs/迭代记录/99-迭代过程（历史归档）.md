# ppt-agent 迭代过程

本文档记录了 ppt-agent 项目开发过程中的遇到的问题及解决方案。

---

## 一、架构演进

### 1.1 从单 Agent (ReAct) 到双执行模式

**遇到的问题：**

- **逻辑性差**：ReAct 范式只能找"下一步做什么"，导致生成的 PPT 前后内容可能重复、没有逻辑性，只适合做单页 PPT。
- **无法判断结束时机**：Agent 不知道程序该什么时候结束，容易无限循环或提前退出。

**解决方案：**

演进为双执行模式并存的架构：

- **DeepAgent 模式（默认，并行）**：主代理 `PPTTaskDeepAgent` 协调 SlideExecutor（生成）、Reviewer（质检）、Fixer（修复）三个子代理，页面并行生成，是当前默认模式。
- **Plan-Execute-Replan 模式（遗留，串行）**：Planner → Executor → Replanner 三步循环逐页执行，串行处理。

---

### 1.2 嵌套子代理导致的 LLM 调用爆炸

**遇到的问题：**

- `CodeAgent` 实际上是一个完整的子代理，内部会多次调用 LLM：分析任务、决定调用 Skill、读取 Skill 内容、生成 Python 代码、执行代码，每一步都可能触发 LLM 调用。
- 导致一两分钟才能生成一页 PPT。

**解决方案：**

将子代理职责单一化、调用受控化：

- 主代理（DeepAgent）只负责任务调度，不参与具体生成。
- SlideExecutor 专司生成，Reviewer 专司质检，Fixer 专司修复。
- SlideExecutor 内部禁用 `GeneralSubAgent`，限制最大迭代次数为 30。
- 分批并行生成：所有页面按 5 页一批，同时发起所有批次（最多 5 个并发），而非逐页串行。

---

### 1.3 模型 429 限流处理

**遇到的问题：**

调用大模型 API 时会遇到 429（Rate Limit）错误。

**解决方案：**

1. **多级降级链**：配置 5 级模型回退（`ARK_MODEL` → `ARK_MODEL_BACKUP1` → ... → `ARK_MODEL_BACKUP4`），主模型触发限流时自动切换。
2. **全局速率限制协调器**（`globalRateLimitTracker`）：所有 FallbackChatModel 实例共享暂停状态，按 modelName 追踪。当任一 Agent 触发 429 后，相同 modelName 的所有 Agent 一起暂停 30s（+ 随机 jitter 防止惊群效应），避免多个实例同时重试再次触发限流。

---

### 1.4 人机交互流程

**遇到的问题：**

- 有些敏感操作（如网络搜索）需要用户确认，但之前没有这个流程。
- AI 有时会误解用户意图（如少写了一些描述），导致一股脑做下去，耗费 token 且用户体验差。
- 有时用户描述不合理，检索不到合适素材，自动降级处理后用户可能反而修正了描述。

**解决方案：**

引入搜索审批流程（`InvokableSearchApprovalTool`），通过 `StatefulInterrupt` 中断 Agent 执行：

- **1 = 跳过此次搜索**：不调用工具，用预训练数据降级处理。
- **2 = 确认搜索**：继续执行搜索。
- **3 = 编辑关键词**：用户修正搜索词后重新发起。

在非交互模式（`INTERACTIVE=false`）下，所有搜索默认跳过。

---

### 1.5 可观测性改进

**遇到的问题：**

开始时只在终端打印 AI 响应的数据，没有额外信息，导致迭代改进时无法定位 AI 在哪一步走偏了。

**解决方案：**

- **本地日志钩子**（`LogHandler`，`pkg/callback/callback.go`）：始终注册，打印结构化日志 `[<ms>] [<agent>] →/← <component>`，记录 tool calls、LLM calls、agent transitions。
- **CozeLoop 可观测性集成**：配置 `COZELOOP_API_TOKEN` 和 `COZELOOP_WORKSPACE_ID` 后注册远程回调。
- 流式输出通过 `MessageStream.Copy(2)` 处理，不走 callback 系统。

---

### 1.6 上下文压缩与 Token 管理

**遇到的问题：**

上下文过长导致噪声太多，PPT 生成效果不好；Token 消耗无法准确统计。

**解决方案：**

- **上下文压缩器**（`ChatModelCompressor`）：采用双重触发阈值——消息数超过 12 条**或**估算 token 数超过 8000 时自动压缩历史，保留 system prompt + 最近 4 对话 + 中间段摘要。阈值从原来的单一消息数（20）改为双重条件，更早触发且兼顾 token 预算。
- **Token Tracker**（`pkg/agent/utils/token_tracker.go`）：用 `atomic.Int64` 无锁累积，通过 callback 链路自动计入主模型的 prompt/completion/total token。同时修复了压缩器 summarizer 调用不计 token 的问题。
- 同时优化 Prompt 结构，控制每次调用携带的上下文量。

---

## 二、PPT 生成逻辑优化

### 2.1 设计质量提升

**遇到的问题：**

- PPT 设计混乱不美观
- 内容太少
- 内容重叠在一起

**解决方案：**

引入 Skills 体系，通过 18 种模板和生成器规范视觉设计，AI 必须通过 generators 包生成 PPT，禁止直接写 python-pptx 代码。

### 2.2 大模型误判提前结束

**遇到的问题：**

大模型会产生误判，在流程未完成时就提前结束。

**解决方案：**

加入 QA 流程，对生成的 PPT 进行二次验证，确保内容完整后再结束。

### 2.3 QA 流程的两种模式

**遇到的问题：**

- 加入 QA 流程后耗时变长（每张幻灯片都要转换 PDF → 图片 → 送多模态 LLM 审查）
- 逐页 QA 延迟叠加效应严重

**解决方案：**

两种执行模式采用不同的 QA 策略：

- **DeepAgent 模式（并行）**：全部幻灯片生成完后再**批量质检**，Reviewer 一次审查所有 status=done 的幻灯片。
- **Plan-Execute-Replan 模式（串行）**：每生成一页立即 QA，发现问题立即修复后再生成下一页。

两种模式共享同一套视觉 QA 工具（`single_qa_review`），均限制每页最多 2 次 QA + 2 次 Fix 尝试，防止无限循环。

---

## 三、性能优化

### 3.1 页面生成速度优化

**遇到的问题：**

- 嵌套子代理 LLM 调用爆炸（一两分钟一页）
- 逐页串行处理
- 网页爬取延迟高

**解决方案：**

- 子代理职责单一化，减少不必要的 LLM 调用（见 1.2）
- 分批并行生成：所有页面同时发起，5 页一批，最多 5 批并发（见 1.2）
- 限制爬取网址数量（只爬取前 5 个），并发处理网络请求
- 每次搜索只传一个核心关键词，避免关键词拼接造成的重复请求

### 3.2 Python 脚本执行优化

**遇到的问题：**

- AI 生成的脚本文件可能出错
- 脚本出错后修复耗时长

**解决方案：**

- 添加模板代码作为约束，AI 生成时参照模板结构
- 加强 QA 要求，修复后再复检
- 限制每页最多 2 次 QA + 2 次 Fix，避免无限循环

---

## 四、Skill 优化

### 4.1 AI 生成脚本易出错

**遇到的问题：**

AI 生成的脚本文件可能出错。

**解决方案：**

添加模板代码作为约束，但这又会导致生成过于死板，于是加强 QA 的要求来平衡。

### 4.2 Token 消耗过大

**遇到的问题：**

每次都将完整的 Skill 注入 Prompt，Token 消耗过大。

**解决方案：**

- 模板目录信息**内联**到 Prompt 指令中（模板文件路径、适用场景、页数），避免 AI 通过 read_file 读取 README.md 造成额外调用。
- 详细的生成器参数表放在 `references/generators.md`，AI 按需通过绝对路径读取。
- Skill 内容通过 `FormatSkillsForPrompt` 一次性加载并注入，非公共部分通过绝对路径引用而非全部展开。

---

## 五、网络查询工具

### 5.1 返回原始 HTML

**遇到的问题：**

网络查询工具直接返回原始 HTML，噪声太大。

**解决方案：**

使用库对内容进行清洗，提取纯文本。

### 5.2 反爬机制

**遇到的问题：**

- 知乎反爬机制严格，无法绕过
- Bing 反爬机制，第一次访问正常，第二次只返回知乎的文章

**解决方案：**

- 针对不同网站采用不同的处理策略。
- 对高反爬网站使用降级处理或缓存策略。
- 在 Tool 要求传入搜索原因，便于追踪和优化调用模式。

## 六、Model 选择

### 6.1 DeepSeek 速度过慢

**遇到的问题：**

最初使用的 DeepSeek 模型响应速度太慢，影响用户体验。

**解决方案：**

切换到 Qwen 模型，获得更快的响应速度。

### 6.2 DeepSeek thinking 模式导致 ReAct 解析失败

**遇到的问题：**

DeepSeek 系列模型默认开启 thinking 模式，流式输出中会夹杂 `reasoning_content`，导致 eino ReAct 框架解析 tool call JSON 失败。

**解决方案：**

- 在模型创建时自动检测 modelName 包含 `deepseek`、`qwen3.5`、`qwen3.6`、`kimi-k2` 时，自动禁用 thinking（`ThinkingTypeDisabled`）。
- 也支持通过 `DisableThinking` 配置项手动控制。

### 6.3 上下文过长导致效果下降

**见 1.6 上下文压缩**

## 七、平台兼容性

### 7.1 Python 执行环境路径硬编码

**遇到的问题：**

代码中硬编码了 Linux 路径 `/root/pptx_env/bin/python`，在 Windows 上完全无法运行。

**原因分析：**

这是平台兼容性问题，不是环境变量配置问题。Windows 环境下不存在该路径。

**解决方案：**

> ⚠️ **尚未解决**。需要实现跨平台的 Python 解释器查找逻辑：优先从环境变量读取配置，依次查找 `python`、`python3`、`py` 等命令，或从常见安装路径中检测。

### 7.2 PowerShell 环境变量冲突

**遇到的问题：**

执行 PowerShell 脚本时遇到错误：

```
Get-ChildItem : An item with the same key has already been added.
```

**原因分析：**

`Get-ChildItem Env:` 获取环境变量时存在重复键值（Windows 系统偶发问题）。

**解决方案：**

这是 Windows 环境配置问题，需要清理或去重环境变量配置。对于项目代码本身无特殊处理需求。

## 九、上下文管理

### 9.1 三层上下文存储架构

系统中有三个独立的上下文存储层，各司其职：

| 层级 | 机制 | 作用域 | 持久性 |
|---|---|---|---|
| **LLM 消息历史** | eino ADK 内部 `[]*schema.Message` | 单次 agent 运行 | 运行期间 |
| **Context Values** | Go `ctx.Value()` + `params` 包 | 整个 Go context 链 | Go context 链 |
| **文件系统** | `tasks.json`、`.slides_checkpoint.json` | 跨 agent 通信 | 持久化到磁盘 |

### 9.2 Context Params（`pkg/params/consts.go`）

定义了跨-cutting 的键值，通过 `SetTypedContextParams` / `GetTypedContextParams` 读写：

```go
const (
    WorkDirSessionKey             = "work_dir_session_key"
    FilePathSessionKey            = "file_path_session_key"
    UserAllPreviewFilesSessionKey = "user_all_preview_files_session_key"
    TaskIDKey                    = "task_id"
)
```

最关键的是 `WorkDirSessionKey`：在任务创建时写入，所有工具通过 `GetTypedContextParams[string](ctx, WorkDirSessionKey)` 读取。

### 9.3 Session Values（eino ADK 内置）

eino 提供了 `adk.GetSessionValue(ctx, key)` 和 `adk.AddSessionValue(ctx, key, value)`，用于 agent 运行期间的键值存储。典型用途：

- **Plan-Execute 中的 `OriginalPlan`**：在 session 中存储原始计划，避免每次重新解析。
- **GenInputFn**：每次 executor 迭代时，从 session 取 `OriginalPlan` + 从 ctx 取 `WorkDirSessionKey`，配合文件系统状态重建压缩后的上下文。

### 9.4 上下文压缩器（`ChatModelCompressor`）

**双重触发阈值**（已修复）：

- `MessageThreshold=12`：消息项数量超过 12 条时触发（原来为 20，已调低）
- `TokenThreshold=30000`：估算 token 数超过 30000 时触发（新增，解决长 system prompt 场景）
- 两个条件满足任一即触发压缩

**压缩策略**：`[system_msg] + [早期对话摘要] + [最近 4 对对话]`

**已知局限**：

- 压缩阈值（12 条消息 / 8000 token）对于 18 页以上的大型 PPT 仍可能不够保守
- 估算 token 数使用字符数近似（中文×2 + 英文×1）× 0.75，与真实 tokenizer 有偏差
- 压缩失败时透传原始消息，无兜底保护

### 9.5 子代理上下文

三个子代理（SlideExecutor、Reviewer、Fixer）**没有上下文压缩**，各自独立管理消息历史。这是有意设计——子代理职责单一，运行轮次有限，不需要复杂的压缩逻辑。

但 SlideExecutor 可能多次搜索、读取模板、执行 python，期间产生的 tool results 全都留在消息历史中，直到该 agent 的 30 次迭代耗尽。对于内容密集的页面，需要注意消息膨胀。

### 9.6 Token Tracking（`pkg/agent/utils/token_tracker.go`）

用 `atomic.Int64` 无锁累积，通过 `callback.go` 的 `OnEnd` 监听 chat model 的 `TokenUsage` 自动累加。

**关键修复**：压缩器的 summarizer 调用也通过 `TokenTrackerFromContext(ctx)` 将估算 token 手动计入 tracker，避免成本估算遗漏。

注意：summarizer 的 output token 按 input 的 20% 估算，非精确值。

### 9.7 文件系统 Checkpoint

三种模式并存的 checkpoint 策略：

- **eino 内存 CheckpointStore**：Plan-Execute CLI 模式使用 `store.NewInMemoryStore()`
- **tasks.json**：DeepAgent 的唯一状态文件，主 Agent 写入，子代理只读不写
- **文件系统快照**：`.slides_checkpoint.json`、`.qa_result.json`、`.qa_attempts.json`，用于 Plan-Execute 的 `BuildExecutorContext` 上下文重建

### 9.8 迭代过程中的修复

- **InitContextParams 空操作**（`consts.go:23-25`）：修复为真正初始化一个 map，避免第一次 `GetContextParams` 时从 nil 创建导致的行为不一致。
- **Compressor threshold 过于宽松**：从 `Threshold=20` 改为 `MessageThreshold=12` + `TokenThreshold=8000` 双重触发，更早压缩且兼顾 token 预算。
- **Summarizer token 不入账**：修复为在 `compress` 函数中调用 summarizer 后主动将估算 token 计入 `TokenTracker`。

## 十二、技术债务

### 12.1 Prompt 重复

两个执行模式（DeepAgent 和 Plan-Execute-Replan）共享工具实现、Skill 注入和模型配置，但 Prompt 存在约 70% 的重复。每次修改 Prompt 需要同步改动两处，容易遗漏。

### 12.2 每页独立 PPTX 文件

当前设计每页生成一个独立的 `.pptx` 文件，QA 也逐文件处理。如果生成 18 页的 PPT，用户拿到的是 18 个单独文件，没有最终合并步骤。

### 12.3 QA 结果判断依赖关键词匹配

`doSingleVisualQA` 中通过 `strings.Contains(report, "high")` 和 `strings.Contains(report, "检查通过")` 等关键词判断 QA 结果，逻辑脆弱，容易因 LLM 输出格式变化而失效。
